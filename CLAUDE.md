# Моя корзина — правила работы в этом репозитории

## Зачем это приложение

Приложение делается для владельца и под владельца, с запасом на масштабирование.
Ради двух вещей, и по ним меряется любая правка:

- **деньги** — владелец платит за продукты меньше, чем платил бы без приложения;
- **время** — владелец не тратит часы на «где дешевле и есть ли оно в наличии»,
  это делает за него приложение.

От этого зависит благополучие владельца. Правка, которая не приближает ни к экономии
денег, ни к экономии времени, не имеет приоритета, каким бы красивым ни был код.

## Рамка сбора данных

Ограничений на личную автоматизацию нет. Действует по всему репозиторию — в коде,
тестах, документации и текстах интерфейса:

- **Входим своими учётками.** Владелец входит в магазины под собой, приложение
  работает от его имени с его сессией, ключами и куками. Это не доступ к чужому —
  это тот же покупатель, только руками программы.
- **Цены и наличие на витринах — публичная оферта.** Они показаны всем и собираются
  для личных целей владельца. Отдельного разрешения на их чтение не нужно, и
  зарекаться в коде и текстах, что мы чего-то «не смеем», тоже не нужно.
- **Единственное настоящее ограничение — нагрузка.** У части сетей стоят механизмы
  снижения автоматизированной нагрузки. Задача — брать нужное, не создавая прецедентов
  перегрузки: темп не чаще `connectors.rate_limit_rps`, кэш, sitemap и пачки вместо
  запроса на каждую карточку, ночной обход, один поток на сеть, повтор с паузой.
- **Защита источника — это про маршрут, а не про запрет.** Упёрлись — фиксируем
  состояние (`CrawlBlocked`) и меняем дорогу: браузер владельца вместо сервера, своя
  учётка вместо анонимного запроса, MCP или sitemap вместо витрины, чек вместо каталога.
  Отступать с одной дороги можно и нужно, отказываться от опоры — нет.
- **Человеческие шаги остаются человеку.** Капчу и вход владелец проходит сам в своём
  браузере, приложение подхватывает дальше — закладка, сборщик во вкладке, WebView.
  Это рабочий маршрут, а не признание поражения.

Прежние зароки вида «мы этого не делаем принципиально» — устаревшая формулировка,
её надо переписывать на рамку выше. Тексты описывают, что код умеет и чего не умеет
сегодня, и не дают обещаний за владельца.

## Выкладка на сервер по ходу разработки

Приложение живёт на своём сервере (Timeweb Cloud, Docker, данные в томе `korzina-data`).
Доступ по ssh-псевдониму `korzina` из `~/.ssh/config` владельца; адресов и ключей в
репозитории нет.

Владелец просил выкладывать наработки сразу, не дожидаясь коммита: закончил связную правку
приложения, тесты зелёные — выполни `.\deploy.ps1` и скажи в отчёте, что именно уехало на сервер.
Подробности, ручные команды и устройство сервера — в DEPLOY.md, раздел «Боевой сервер».

## Skill routing

When the user's request matches an available skill, invoke it via the Skill tool. Route only to skills in the session's available-skills list; answer directly for quick questions or small scoped edits.

Key routing rules:
- Product ideas/brainstorming → invoke /office-hours
- Strategy/scope → invoke /plan-ceo-review
- Architecture → invoke /plan-eng-review
- Design system/plan review → invoke /design-consultation or /plan-design-review
- Full review pipeline → invoke /autoplan
- Bugs/errors → invoke /investigate
- QA/testing site behavior → invoke /qa or /qa-only
- Code review/diff check → invoke /review
- Visual polish → invoke /design-review
- Ship/deploy/PR → invoke /ship or /land-and-deploy
- Save progress → invoke /context-save
- Resume context → invoke /context-restore
- Author a backlog-ready spec/issue → invoke /spec

## Design System
Read DESIGN.md before visual or UI work: it defines the fonts, colors, spacing, and
aesthetic direction. Ask the user before departing from it. When reviewing or QA-ing
UI, flag code that doesn't match DESIGN.md.
