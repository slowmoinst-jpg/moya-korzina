# Развёртывание

## Где живёт приложение

На своём сервере в Timeweb, в контейнерах, и больше нигде. Выбор площадки закрыт
решением владельца 17.09.2026 — «Streamlit и GitLab уже не нужны, мы перешли на
выделенный сервер», — поэтому прежняя таблица с Render, Railway, Fly.io и
Streamlit Community Cloud отсюда убрана: сравнивать больше нечего, а устаревшая
таблица хуже её отсутствия. Устройство сервера — ниже, в разделе «Боевой сервер».

Что из прежнего разбора стоит помнить, потому что оно объясняет форму решения:

- **Serverless не годится в принципе.** Streamlit — это долгоживущий сервер на
  Tornado: он держит WebSocket с каждой вкладкой и хранит состояние сессии в
  памяти процесса. Функция, которая умирает после запроса, такого не выдержит.
- **Данные лежат файлами.** SQLite пишет в `data/basket.db`, базы людей — в
  `data/users/<номер>/`, общий каталог — в `data/catalog.db`, кэш цен — в
  `data/cache/`. Всё это требует постоянного диска, а не эфемерного.
- **Том монтируется в `/app/data`, и это не деталь.** Смонтируете не туда — при
  первой же выкладке пропадут чеки, сопоставления, история цен и подключения
  магазинов. Образ ([Dockerfile](Dockerfile)) читает порт из `PORT` и слушает
  `0.0.0.0` — это осталось от переносимости и мешать не мешает.

Репозиторий к выкладке отношения не имеет: `deploy.ps1` пакует РАБОЧЕЕ ДЕРЕВО и
кладёт его на сервер по ssh. Ни GitHub, ни любой другой хостинг кода в этой цепочке
не участвует — он нужен только как место, где код лежит не на одном диске.

## Что нужно помнить, раз адрес публичный

1. **Вход есть, но пока без подтверждения.** Рабочее место открывается по номеру
   телефона без пароля и без кода (`app/users.py`, решение владельца 16.09.2026):
   кто знает номер, тот и войдёт. На экране входа об этом сказано словами. Код из
   СМС появится вместе с загрузкой чеков из кабинета ФНС, где он нужен и так.
2. **Данные людей разложены по базам.** Каждому номеру своя `data/users/<номер>/basket.db`;
   общий каталог и очередь адресов — в `data/catalog.db`, один на сервер. Демо —
   отдельное рабочее место с вымышленными данными.
3. **У приёмной двери нет HTTPS.** `app/api.py` слушает 8765 открытым текстом, и
   секрет рабочего места едет по сети как есть. Лечится обратным прокси с
   сертификатом перед обоими контейнерами; до тех пор лекарство — смена секрета
   одним нажатием на экране «Магазины».
4. **Ключи и секреты — на сервере, не в репозитории.** Токены кабинета ФНС лежат в
   базе рабочего места, секрет двери — там же. В git ничего этого нет и быть не должно.

## Локальный запуск в контейнере

```bash
docker build -t korzina .
docker run --rm -p 8501:8501 -v korzina-data:/app/data korzina
```

Первый запуск создаёт пустую базу. Демо-данные наливаются командой:

```bash
docker run --rm -v korzina-data:/app/data korzina python tools/seed.py
```

## Боевой сервер

С 16.09.2026 приложение живёт на своём VPS в Timeweb Cloud (Ubuntu 26.04, Docker из репозитория
Ubuntu). Адрес, пользователь и ключ в репозитории не хранятся: они в `~/.ssh/config` владельца под
псевдонимом `korzina` (ключ `id_ed25519_korzina_deploy`). Проверить доступ: `ssh korzina hostname`.

| Что | Где на сервере |
|---|---|
| Исходники последней выкладки | `/opt/korzina/src` — распакованный архив рабочего дерева |
| Журнал последней сборки | `/opt/korzina/build.log` |
| Образ и контейнер | `korzina:latest`, контейнер `korzina`, порт 80 → 8501, `--restart unless-stopped` |
| Данные: база и кэш цен | том `korzina-data`, смонтирован в `/app/data`; передеплой его не трогает |

Выкладка одной командой с рабочей машины:

```powershell
.\deploy.ps1          # упаковать рабочее дерево, собрать образ на сервере, перезапустить
.\deploy.ps1 -Test    # сначала тесты, выкладка только если зелёные
.\deploy.ps1 -Seed    # после выкладки пересоздать демо-данные в базе на сервере
```

Скрипт упаковывает ровно то, что копирует Dockerfile (без `.git`, `.venv`, тестов, базы и кэша),
заливает архив по `scp`, а серверную часть делает [tools/server-deploy.sh](tools/server-deploy.sh):
собирает образ, при удачной сборке меняет контейнер и ждёт ответа `/_stcore/health`. Если сборка
не удалась, старый контейнер продолжает работать. Правило проекта: наработки выкладываются сразу
по ходу разработки, не дожидаясь коммита (см. [CLAUDE.md](CLAUDE.md)).

Полезное на сервере:

```bash
ssh korzina docker logs --tail 50 korzina
ssh korzina docker exec korzina python tools/seed.py
ssh korzina docker restart korzina
```

Авторизации у приложения по-прежнему нет (см. «Что обязательно сделать до публичного адреса»):
всё, что вы в него загрузите, увидит любой, кто знает адрес.

Docker Hub с этого сервера отвечает `429 Too Many Requests` на анонимные запросы манифестов
(лимит на адрес), из-за чего сборка может упасть ещё на `FROM`. Поэтому в `/etc/docker/daemon.json`
прописаны зеркала `mirror.gcr.io` и `dockerhub.timeweb.cloud` и включён `live-restore`: контейнер
переживает перезапуск демона. Если сборка снова упрётся в реестр, смотрите `/opt/korzina/build.log`.

### Базы людей и демо

С 16.09.2026 вход по номеру телефона, и у каждого номера своя база:
`data/users/<номер>/basket.db` внутри тома `korzina-data` (на сервере — `/app/data/users/…`).
Общая `data/basket.db` из config.yaml приложением больше не читается; она осталась для
тестов и утилит. Настоящие рабочие места начинаются пустыми, демо-данные наливаются
только в рабочее место `demo` — само при первом открытии или командой:

```bash
ssh korzina docker exec korzina python tools/seed.py demo
```

Старую общую базу владельца переносит `tools/adopt_legacy_db.py <номер>` (копирует, не
удаляет). Ключи кабинета ФНС (app/fns) лежат в той же базе человека, в таблице settings.

### Планировщик каталога

Вместе с приложением `tools/server-deploy.sh` поднимает второй контейнер `korzina-jobs`
из того же образа и с тем же томом: он раз в сутки (`catalog.refresh_at` в config.yaml)
обходит каталоги сетей и сопоставляет товары (`app/catalog/worker.py`), а при пустом
каталоге начинает сразу после выкладки. Общая база каталога — `data/catalog.db` в томе.

```bash
ssh korzina docker logs --tail 50 korzina-jobs              # ход обхода
ssh korzina docker exec korzina python -m app.catalog.worker --once --chain magnit   # одна сеть сейчас
ssh korzina docker exec korzina python -m app.catalog.worker --match                 # только сопоставление
```

Устройство каталога, сборщики по сетям и границы — docs/design/catalog-2026-09-16.md.

**Внеочередной обход всех сетей** — отдельным контейнером: выкладка сносит `korzina` и
`korzina-jobs`, а его не трогает.

```bash
ssh korzina 'docker run -d --name korzina-crawl-$(date +%d%m) -v korzina-data:/app/data \
    --env-file /opt/korzina/llm.env korzina:latest python -m app.catalog.worker --once'
ssh korzina docker logs -f korzina-crawl-$(date +%d%m)
```

С двумя обходами разом ничего не случится: они ждут друг друга на замке
`data/crawl.lock` (`worker.one_crawler`), а плановый обход пропускает сети, обойденные
без ошибок за последние `catalog.fresh_hours` часов (12). Поэтому вечерний внеочередной
обход не удваивается ночным.

### Домашний выход: сети, которые не пускают сервер

Серверу Дикси отказывает по адресу дата-центра, а через домашний интернет владельца
отдаёт витрину с ценами (замер 25.09.2026). Устройство:

- на ноутбуке владельца служба пользователя `korzina-tunnel` держит
  `ssh -N -R 127.0.0.1:1080 korzina-tunnel@<сервер>` — SOCKS-выход на сервере
  ([tools/tunnel/laptop-setup.sh](tools/tunnel/laptop-setup.sh));
- на сервере пользователь `korzina-tunnel` без оболочки, его ключ умеет только держать
  туннель ([tools/tunnel/server-setup.sh](tools/tunnel/server-setup.sh)); заводит его владелец;
- мост `korzina-tunnel-relay` (его поднимает `server-deploy.sh`) пускает к туннелю
  контейнеры: `172.17.0.1:1080` → `127.0.0.1:1080`;
- какие сети ходят через дом — `connectors.home_exit` в config.yaml, сейчас Дикси, Пятёрочка, Самокат, Магнит.

```bash
ssh korzina 'ss -ltn | grep :1080'     # туннель жив; пусто — ноутбук выключен, спит или вход не выполнен
```

Нет туннеля — сборщик идёт как раньше, без цен с витрины, и пишет в журнал почему.

### Корзины — в кабинеты магазинов

Пачка проходит кнопки «Результата» за человека: по каждому рабочему месту (кроме демо)
берёт последнюю корзину, вариант, который экран показывает первым, и кладёт его в
кабинеты сетей тем же пускателем, что кнопка «Передать». Лента и ВкусВилл отдают
корзину ссылкой — пачка печатает её. Сети, куда корзину не положить, названы с причиной.

```bash
ssh korzina docker run --rm --name korzina-carts -v korzina-data:/app/data korzina:latest \
    python -m app.cartfill --dry-run     # что будет сделано; ничего не кладёт
ssh korzina docker run --rm --name korzina-carts -v korzina-data:/app/data korzina:latest \
    python -m app.cartfill               # положить (--phone, --basket — сузить)
```

По расписанию её не пускают: каждый прогон кладёт товары в корзину заново.

### Ключ модели

Запасной разбор страницы языковой моделью (`app/connectors/smart_extract.py`) включён в
config.yaml и ходит в OpenRouter. Ключ лежит на сервере **рядом с исходниками, а не в
них** — в `/opt/korzina/llm.env`, правами `600`, одной строкой:

```
OPENROUTER_API_KEY=sk-or-v1-...
```

Почему не в `/opt/korzina/src`: выкладка распаковывает туда архив рабочего дерева
целиком, и ключ, положенный внутрь, исчез бы при следующей же выкладке. `server-deploy.sh`
подхватывает файл сам (`--env-file`) и передаёт обоим контейнерам — приложению и
планировщику. Файла нет — приложение работает как раньше, а запасной разбор молчит и
пишет в журнал, какой переменной ему не хватает.

Проверить канал целиком — ключ, адрес, модель, разбор ответа:

```bash
ssh korzina docker exec korzina python tools/smartcheck.py
```

Он спрашивает модель про нарочно сломанную карточку и печатает, что она ответила и за
сколько секунд. Молча «не сработало» тут не бывает: причина называется вслух.

Смена модели — `connectors.smart_extract.model` в config.yaml. Первое слово до косой
черты выбирает поставщика (`openrouter`, `deepseek`, `openai`, `anthropic`, `ollama`),
остальное — название модели у него. Для рассуждающих моделей OpenRouter рассуждение
выключается кодом: без этого ответ упирается в потолок токенов и приходит пустым.

**До кого сервер дотягивается, а до кого нет.** Замер с боевого сервера от 19.09.2026,
простым `curl` по адресу перечня моделей — то есть ещё до всякого ключа:

| Шлюз | Ответ | Что это значит |
|---|---|---|
| `openrouter.ai` | **403** | закрыт для нашего адреса |
| `api.openai.com` | **403** | закрыт для нашего адреса |
| `api.anthropic.com` | **403** | закрыт для нашего адреса |
| `api.deepseek.com` | 401 | связь есть, не хватает только ключа |
| `api.mistral.ai` | 401 | связь есть, не хватает только ключа |

403 приходит и на публичный перечень моделей, где ключ не участвует вовсе, — значит
дело в адресе сервера, а не в ключе. Ключ OpenRouter поэтому работает с машины
владельца и НЕ работает с сервера: в журнале это видно строкой
`Access denied by security policy`.

Дороги отсюда три, и выбор за владельцем: ключ DeepSeek на `api.deepseek.com` (связь
уже есть, модель та же), прокси для исходящих запросов сервера, или `ollama` прямо на
сервере — тогда наружу не идёт ничего, но 7,7 ГБ памяти придётся делить с обходом
каталога.

Выкладки из нескольких сессий выстраиваются в очередь: у каждой свой архив
`/opt/korzina/src-<метка>.tgz`, а распаковка и сборка идут под замком
`/opt/korzina/deploy.lock` (flock). Без этого вторая выкладка удаляла папку исходников
из-под сборки первой, и та падала с «getwd: no such file or directory».
